# 2026-08-28 — 견적대로 45%만 들어냈다

**태그:** `#portfolio`

[6일 전에 3D 재작성 견적을 냈다](2026-08-22-boundary-pays-off-in-3d.md) — `Scripts/UI/`의
3,776줄만 다시 쓰고 나머지 55%는 그대로 간다는 계산이었다. 오늘 그걸 실제로 실행했다.
**견적이 맞았다.** 이 문서는 그 실행의 기록과, 실행하면서 견적에 없던 것들이 뭐였는지다.

## 실제로 일어난 일

`MatchScreenUI`(1,063줄), `HandView`, `DeckView`, `CardView`, `CardDropZone`,
`CardTooltipView`, 카드 이펙트 5종, `MatchScreen.tscn`, `Scenes/Match/` 8개, 셰이더 2개와
머티리얼 2개를 [Deprecated/](../Deprecated/)로 옮겼다. 자리에는
[Scenes/Screens/MatchWorld.tscn](../Scenes/Screens/MatchWorld.tscn) —
탁상, 마주 보는 좌석 둘, 스포트라이트, 착석 시선 높이의 카메라 — 이 들어갔다.

**`GameLogic`, `GameState`, `MatchView`, RPC 흐름, 테스트 134개는 한 줄도 안 건드렸다.**
빌드도 테스트도 처음부터 끝까지 초록색이었다. 화면을 통째로 들어내는 작업에서 이게
가능했다는 게 견적의 핵심이 실물로 확인된 지점이다.

`MatchWorldView`가 `MatchScreenUI`와 **같은 신호를 구독한다.** `RoundResolved`가 오면
`View.LastRoundOutcome`과 `View.MyCard`를 읽어서 이긴 쪽 캐릭터에게 이긴 카드에 맞는 동작을
재생시킨다. 규칙 판정은 이미 끝나 있고 이 클래스는 애니메이션만 고른다 — 2D 때
`Scripts/CLAUDE.md`에 적어둔 "이 레이어는 누가 이겼는지 판단하지 않는다"가 3D에서도
글자 그대로 유지됐다.

## 견적에 없던 것 1 — 설계 자체가 바뀌었다

견적은 "같은 게임을 3D로"를 가정했다. 그런데 오늘 설계가 뒤집혔다.

| | 이전 ([ASSETS-3D.md](../ASSETS-3D.md)) | 지금 |
|---|---|---|
| 시점 | 1인칭, 팔만 | 3인칭, 얼굴·상반신 보임 |
| 상대 | 팔만, 얼굴 없음 | 전신 캐릭터 |
| 승패 | 10선승 | 체력, 승리 수단마다 다른 피해 |
| 능력카드 | 카드로 냄 | 아이템/스킬로 분리 예정 |

승리 수단별로 연출이 갈린다 — 바위로 이기면 얼굴 강타(-2), 가위면 왼손 고정(-1),
보면 책상 내려쳐 패 공개(-1). **이건 연출이 아니라 규칙이다.** 체력도, "다음 턴만 고정"
같은 라운드를 넘어가는 상태도 지금 `GameLogic`에 없는 개념이라 거기부터 손대야 한다.

`ASSETS-3D.md`는 이제 상당 부분이 무효다. 지우지 않고 문서 머리에 경고만 달았다 —
조명·안개·임포트 설정·치수처럼 시점과 무관한 절들은 여전히 유효해서다.

## 견적에 없던 것 2 — 엔진을 갈아탈 뻔했다

"3D면 언리얼로 가야 하나"를 검토했고, **안 가기로 했다.**

언리얼에서 C++ 클래스는 텍스트라 잘 다뤄지지만, **블루프린트와 애님 블루프린트는 에디터
전용 그래프에 바이너리에 가까운 `.uasset`**이다. diff도 텍스트 편집도 안 된다. 이 프로젝트가
지금까지 `.tscn`을 직접 텍스트로 고치고 헤드리스로 검증하며 굴러온 방식이 통째로 막힌다.
게다가 언리얼 관행상 게임 로직의 상당 부분이 블루프린트로 가므로, 그 부분이 전부 워크플로우
바깥에 남는다.

기능 자체는 Godot에 다 있었다:

| 언리얼 | Godot 4 |
|---|---|
| AnimNotify | `AnimationPlayer`의 Call Method 트랙 |
| Montage | `AnimationTree`의 `AnimationNodeOneShot` |
| Socket | `BoneAttachment3D` |
| 리플리케이션 | 이미 쓰고 있는 하이레벨 멀티플레이어 API |

약한 곳은 **런타임 IK**(Control Rig 대비)뿐인데, 이 게임엔 실시간 IK가 필요한 연출이 없다.
전부 미리 구운 애니메이션이라 엔진의 IK 지원 수준과 무관하다.

## 견적에 없던 것 3 — Blender 파이프라인에서 실제로 데인 것

작업 순서는 **IK로 애니메이션 → Bake(Visual Keying) → NLA 트랙 → glTF export**로 정착했다.
그 과정에서 두 번 데었다.

**`Clear Local Constraints`는 액션이 아니라 리그에 걸린다.** 컨스트레인트는 아마추어에
붙어 있어서 모든 액션이 공유한다. 첫 액션을 구우면서 이 옵션을 켜면 IK가 그 자리에서
사라져 나머지 액션을 못 굽고, 반대로 안 끄고 새 IK를 추가하면 **이미 구워둔 액션들에
소급 적용되어 NLA 스트립이 전부 꼬인다.** 결론은 액션 하나 구울 때마다 컨스트레인트를
정리하고 다음 작업 전에 다시 붙이는 것. 구워진 키프레임 자체는 안 망가지므로 꼬인 것은
컨스트레인트만 지우면 되살아난다.

**glTF에 IK는 안 실린다.** 베이킹이 IK를 가져오는 유일한 방법이고, `Clear Local Constraints`는
export와 무관한 블렌더 안 정리용이다. 이름이 비슷해서 둘을 같은 것으로 착각하기 쉽다.

**NLA는 스트립이 아니라 트랙 단위로 나간다.** 유니티 때처럼 한 트랙에 스트립을 늘어놓고
임포터에서 구간을 자르는 방식이 아니라, **애니메이션마다 트랙을 따로** 만들어야 클립이
나뉜다. 트랙 이름이 곧 Godot 클립 이름이 된다.

## 견적에 없던 것 4 — 소스 파일은 프로젝트 안에서 inert하지 않다

`.blend`와 Mixamo `.fbx`를 `Assets/`에 두었더니 **Godot이 `.fbx`를 임포트하면서 텍스처 4장을
뽑아 옆에 뿌렸다.** `.gitignore`는 이걸 못 막는다 — 파일이 디스크에 그대로 있으니 에디터는
계속 읽는다.

`Assets/_Source/`를 만들고 `.gdignore`를 넣었다. `.gitignore`(저장소에서 제외)와
`.gdignore`(Godot이 스캔 안 함)는 **다른 문제를 푸는 서로 다른 장치**이고 둘 다 필요하다.
`Deprecated/`가 이미 같은 방식을 쓰고 있었는데(거기다 `.csproj`의 컴파일 제외까지 셋),
그 패턴을 뒤늦게 한 번 더 확인한 셈이다.

## 마지막 — 추측 대신 측정

임포트한 캐릭터가 어느 쪽을 보는지 몰라 회전을 못 정하고 있었다. 두 번 추측해서 두 번
틀렸다. 결국 임시 GDScript로 발끝−발목 벡터를 월드 공간에서 계산했다.

처음 계산은 **틀렸다.** 씬 트리에 제대로 안 들어간 노드의 `global_transform`이 단위행렬로
나와서, 캐릭터가 "57미터짜리로 누워 있다"는 결과가 나왔다. `Armature` 노드가 물고 있는
변환(0.01 스케일 + −90° X 회전)을 직접 반영해 다시 계산하니 **키 1.69m, 정면 +Z**로
깔끔하게 떨어졌다.

교훈은 측정이 추측보다 낫다는 뻔한 얘기가 아니라, **측정도 틀릴 수 있으니 결과가
말이 되는지(사람 키가 1.7m인지) 봐야 한다**는 쪽이다. 57미터가 안 이상해 보였으면
그대로 믿었을 것이다.
