# 2026-08-18 — 두 인스턴스 실검증, 그리고 안 하기로 한 것들

[2026-08-17-multiplayer-autoload-layer.md](2026-08-17-multiplayer-autoload-layer.md)가 "씬이 없어서 두 인스턴스 검증을 못 했다"로 끝났다. 이 문서는 그 검증을 실제로 돌린 기록 — 그리고 그 과정에서 나온 버그 2개, 구조를 **안 바꾸기로** 한 결정, 새로 확정한 게임 규칙 1개.

## 검증용 하네스를 만들고 실제로 돌림

`Scenes/MatchDebugUI.tscn` + `Scripts/UI/MatchDebugUI.cs`. 씬 파일에는 `Control` 노드 하나뿐이고 레이아웃은 전부 코드로 만든다 — 검증이 끝나면 통째로 버릴 물건이라 에디터에서 배치할 이유가 없었다.

호스트/조인/매치시작 버튼, 손패 버튼 줄, 로그 창. `GameState.Instance.View`만 읽고 `_session`은 쳐다보지 않는다. 호스트에서도 마찬가지 — 이건 `Scripts/CLAUDE.md`의 규칙이고, 디버그 코드라고 예외를 두면 규칙이 지켜지는지 확인할 방법이 없어진다.

**결과: RPC 왕복이 실제로 돈다.** 접속, 매치 시작, 카드 제출, 라운드 해결 브로드캐스트, 개인 패 전달, 승패까지 두 인스턴스로 확인. 컴파일은 되면서 런타임에 틀릴 수 있는 종류(`RpcMode` 오지정, 전송 불가 인자 타입)가 이제 걸러졌다.

## 버그 1 — 클라이언트 손패가 한 라운드 뒤처짐

코드를 읽다 발견 (실행 전).

`PrivateHandRpc`가 `View.MyHand`를 갱신하는데 **시그널을 아무것도 안 쐈다.** 그런데 이 RPC는 공개 브로드캐스트인 `RoundResolvedRpc`보다 **뒤에** 도착한다. 순서가 이렇게 된다:

```
RoundResolvedRpc  도착 → RoundResolved 시그널 → UI 다시 그림 (아직 옛 손패)
PrivateHandRpc    도착 → MyHand 갱신 → 아무도 모름 → 화면은 그대로
```

결과적으로 클라이언트 화면은 계속 **직전 라운드의 손패**를 보여준다. 호스트는 `_session`에서 직접 복사하니 멀쩡해서, 두 인스턴스를 나란히 놓고 봐야만 보이는 종류.

→ `MyHandChanged` 시그널을 추가하고 `View.MyHand`를 대입하는 4곳 전부에서 발행. 대입 지점과 발행 지점을 1:1로 묶어두면 나중에 대입만 추가하고 발행을 빠뜨리는 실수가 줄어든다.

## 버그 2 — 교체가 자기 자신을 덱에 넣으면 매치가 굳음

이쪽이 훨씬 심각했다.

발단은 "변화가 안 된다"는 플레이 리포트였는데, 그건 사실 하네스 한계였다 — 당시 하네스는 모든 카드를 `CardPlay.WithoutChoice()`로 보냈고, 변화는 "무엇을→무엇으로"가 실려야 하니 호스트가 정상적으로 거부한 것. **즉 버그가 아니라 의도대로 동작한 것.**

다만 그 말은 변화/교체의 RPC 경로가 **한 번도 실행된 적이 없다**는 뜻이기도 해서, `RoundResolver`의 실행 순서를 다시 훑어봤다가 다른 걸 찾았다.

`RoundResolver.Resolve`의 순서:

```
1. 각 카드의 fate/승패 계산
2. ApplyFate  ← 낸 카드를 손패에서 제거 (여기!)
3. RunSpecialEffectsInPriorityOrder  ← 효과는 이제야 실행
4. 양쪽 드로우
```

2번이 3번보다 먼저인 건 의도적이다 — 리셋이 "내 손패 전부 덱으로" 할 때 리셋 자신이 손패에 남아 있으면 안 되니까. 그런데 `SwapEffect.Validate`는 **제거 전 손패**를 보고 있었다. 그래서:

- 교체를 내면서 "덱에 넣을 카드"로 **교체 자신**을 지목 → 검증 통과 (그 시점엔 손패에 있음)
- `ApplyFate`가 교체를 제거
- `Apply`가 없는 카드를 빼려다 `Hand.Remove`에서 예외

예외가 터지는 지점이 최악이다. **양쪽 카드가 이미 손패에서 빠져나간 뒤, `AdvanceToNextRound`가 실행되기 전.** 제출 슬롯이 안 비워지니 양쪽 다 "이미 제출함"으로 고정되고, 카드는 조용히 사라진 채 그 매치는 **영영 다음 라운드로 못 간다.**

덱에 교체가 1장씩만 있으니 이 조합은 낼 때마다 100% 재현된다.

→ `Validate`가 **`Apply`가 보게 될 손패**(= 낸 카드를 뺀 상태)를 기준으로 검사하도록 수정. 회귀 테스트를 `SwapEffectTests`와 `MatchSessionTests` 양쪽에 추가하고, 픽스만 stash해서 실제로 실패하는지 확인한 뒤 되돌렸다 (97/2 → 99/0).

### 여기서 배운 것

**`Validate`와 `Apply` 사이에 상태가 변한다.** 이건 `SwapEffect`만의 문제가 아니라 `ICardEffect` 인터페이스 전체에 걸친 함정이다. 지금은 나머지 4개가 우연히 안 걸리지만(자기 카드를 인자로 받는 게 교체뿐), 새 특수카드를 추가할 때 반드시 떠올려야 할 것.

## 하네스를 확장해서 변화/교체를 낼 수 있게 함

변화는 드롭다운 2개, 교체는 손패별 토글 버튼. **규칙 필터링은 일부러 안 넣었다** — 조커를 변화 대상으로 고르는 것도, 교체 목록에서 교체 자신을 켜는 것도 가능하다. 하네스가 규칙을 판단하면 호스트의 거부 경로를 손으로 확인할 방법이 없어진다. 판단은 호스트가, 하네스는 보내기만.

이걸로 `CardPlayCodec`의 미검증 필드(`cardToTransform`/`transformInto`/`cardsToReturn`)도 실제로 전송을 타게 됐다.

## `.cs.uid` 정리

프로젝트를 처음 실행하니 Godot이 `.cs` 옆에 `.cs.uid`를 38개 생성했는데, **`GameLogic/`과 `Tests/`까지 훑고 있었다.** 이 둘은 Godot이 인덱싱할 이유가 없는 순수 .NET 프로젝트다.

→ 두 폴더에 `.gdignore` 추가 (Godot 파일시스템 스캐너가 통째로 건너뜀). 빌드는 MSBuild가 하므로 영향 없음. `Scripts/` 아래 9개는 정상적인 스크립트 신원 파일이라 커밋에 포함.

## 10선승으로 되돌림

5선승으로 낮춰뒀던 걸 다시 10으로. `WINS_NEEDED_FOR_MATCH` 하나만 고치면 되고, 테스트도 하드코딩된 `5` 대신 이 상수를 참조하도록 바꿔서 다음에 또 바뀌어도 테스트는 안 건드리게 했다.

## 구조 결정: `DeckAssembler`는 그대로 둔다

`Deck`/`Hand`/라운드 해결은 전부 `GameLogic`에 있는데 **"덱에 뭐가 몇 장 들어가는가"만 `Scripts/Cards/DeckAssembler.cs`에 있다.** `CardDatabase`(Godot `Resource` 로더)를 읽어야 해서 그렇게 됐고, 결과적으로 덱 조립 규칙에는 테스트가 하나도 없다.

이걸 `GameLogic/DeckComposition`으로 옮기는 안을 검토했다가 **접었다.**

이유: 테스트가 잡아줄 게 실제로 없다. 조립 코드는 분기도, 외부 입력도, 조건도 없는 상수 나열 다섯 줄이고, 매치를 시작할 때마다 100% 실행된다. 여기서 날 수 있는 버그는 상수 오타 정도인데 그건 한 판만 켜봐도 보인다. 테스트가 값을 하는 건 분기가 있고 외부 입력이 있고 눈으로 검증하기 느린 코드이고 — 라운드 해결이 `GameLogic`에 있는 이유가 그거다 — 덱 조립은 셋 다 아니다.

지금 옮기면 `GameLogic`에 파일이 하나 늘고 `DeckAssembler`는 5줄짜리 껍데기가 되는데, 얻는 건 저가치 테스트뿐이다. 루트 `CLAUDE.md`가 금지하는 "나중에 필요할까봐 미리 만드는 스캐폴딩"에 정확히 해당한다.

**분리가 값을 하는 시점은 클라이언트가 자기 덱을 보내오기 시작할 때다.** 그때는 조작 가능한 외부 입력을 호스트가 재검증해야 하고, 그건 진짜 규칙이고 진짜 조합이다. 그때 같이 한다.

> 안 한 일을 기록해두는 이유: 이 판단을 안 남기면 다음에 코드를 훑다가 "덱 조립에 테스트가 없네?" 하고 같은 리팩터링을 또 시작하게 된다.

## 새 규칙 확정: 덱 고갈 = 패배

위 논의 중에 계산하다 발견한 것 — **덱이 바닥나면 지금 크래시난다.** `Deck.TakeFromTop()`이 빈 리스트에서 `_cards[0]`을 인덱싱해서, 라운드 해결 도중에 예외가 터진다. 교체 버그와 **완전히 같은 방식으로 매치가 굳는다.**

지금 안 터지는 이유가 아슬아슬하다:

| | 장수 |
|---|---|
| 시작 덱 | 20 |
| 멀리건 | −6 → 14 |
| 영구 소멸 가능 (더미4 + 조커2 + 특수5) | −11 |
| **최악의 경우 남는 덱** | **3** |

일반카드 9장이 덱 바닥으로 돌아가며 순환하니 소멸 카드 11장만 빠져나간다. **여유 3장은 설계가 아니라 우연이고**, 덱 구성을 손대는 순간 깨진다. `Deck.cs`만 봐서는 자기 안전성이 다른 파일의 카드 비율에 의존한다는 게 전혀 안 보인다.

→ **고갈된 쪽이 매치 패배**로 확정. 드로우가 "예외 없이" 일어나는 게 라운드 진행의 전제이므로, 뽑을 수 없다는 건 게임을 계속할 수 없다는 뜻이라 무승부나 리셔플이 아니라 패배가 맞다고 판단. `DESIGN.md`에 "덱 고갈" 섹션 추가.

**아직 코드에는 없다.** 동시 고갈 / 효과 도중 고갈 두 하위 케이스도 미정으로 남겨뒀다.
