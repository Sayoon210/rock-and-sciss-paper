# 2026-08-29 — 3D 표현 계층에서 밟은 지뢰들

**태그:** `#3d` `#troubleshooting`

머리 시선 조작, 그 동기화, 손패 카메라 블렌드, 카드 오브젝트, 카드 포인터 상호작용까지
붙였다. 결과물은 커밋 4개(`24c8dac`, `306c56a`, `a131548`, `dfe2d88`)에 있다.
**이 문서는 결과가 아니라 그 사이에 틀렸던 것들의 기록이다.** 대부분은 "Godot이 이렇게
동작할 것이다"라는 추측이 틀린 경우였고, 전부 측정으로 잡혔다.

---

## 1. 가장 크게 헤맨 것 — 폐기된 API 하나가 만든 유령

### 증상

머리 본을 마우스로 돌리는 코드를 붙인 직후부터, **내 캐릭터의 얼굴이 화면을 가득 채운
초근접 상태로 카메라에 들러붙었다.** 카메라를 어디에 두든 똑같았다.

### 내가 틀리게 짚은 것들 (순서대로)

| # | 가설 | 왜 틀렸나 |
|---|---|---|
| 1 | 카메라가 머리에 너무 가깝다 | 뒤로 빼도 동일 |
| 2 | 헤드 페이드 범위가 잘못됐다 | 범위를 0.1~3.0으로 극단화해도 안쪽 면은 그대로 보임 |
| 3 | 씬을 저장 안 해서 | 저장 후에도 동일 |
| 4 | 에디터 Play의 빌드 캐시 문제다 | 독립 실행으로도 동일 |

**네 번 다 사용자 워크플로우를 의심했고 네 번 다 틀렸다.** 원인은 내가 방금 넣은 코드에
있었다.

### 실제로 원인을 가른 관찰

사용자가 정확히 짚었다 — *"머리가 돌아간다는 게 아니라 머리만 똑 떨어져서 카메라 위치에
붙어 있다"*, 그리고 *"카메라를 100 100 100 같은 데 둬도 게임 켜면 다시 그 위치로 간다"*.

이게 결정적이었다. 카메라를 극단적 위치로 옮겨도 화면이 똑같다면 **카메라 배치 코드는
용의선상에서 빠진다.** 실제로 측정해서 확인했다:

- yaw를 45도로 고정하고 본의 월드 좌표를 출력 → **본은 움직이지 않았다**
- 카메라를 `(100, 100, 100)`으로 강제 → **화면 변화 없음**

남은 건 본 포즈를 쓰는 API 자체뿐이었다.

### 원인과 수정

`Skeleton3D.SetBoneGlobalPoseOverride` / `GetBoneGlobalPoseNoOverride`. **Godot 4.7에서
둘 다 `[Obsolete]`다** (설치된 `GodotSharp.dll`에 리플렉션으로 확인). 좌표 규약을
확신을 갖고 특정할 수 없었고, 무엇보다 재현 가능한 렌더링 파손을 만들었다.

`SetBonePoseRotation`으로 교체했다. 이건 **부모 본 기준 로컬** 세터라, 원하는 월드 basis를
부모의 월드 basis로 나눠서 넣어야 한다 — 스켈레톤의 `GlobalTransform`이 아니라 **부모 본**
이다. 이 변환은 [BoneLookRotator.cs](../Scripts/Match3D/BoneLookRotator.cs) 한 곳에만 있다.

> **교훈:** 폐기 표시가 붙은 엔진 API는 "아직 동작은 한다"가 아니라 **"동작이 보장되지
> 않는다"**로 읽어야 한다. 그리고 내 가설이 두 번 연속 틀렸으면 세 번째 가설을 세우지 말고
> **측정 대상을 바꿔야 한다.**

## 2. 추측이 틀렸던 것들 — 전부 측정으로 잡음

### `.tscn`의 `Transform3D(...)` 12개 값은 **행(row) 순서**다

축(열)이 아니다. 나는 `Transform3D(a,b,c, d,e,f, g,h,i, ...)`에서 `(a,b,c)`가 X축이라고
읽었고, 그 전제로 "손패 카메라가 카드를 안 보고 있다"는 **틀린 진단**까지 냈다.

헤드리스로 실제 `GlobalTransform`을 찍어보니 y 성분 부호가 반대였다:

```
.tscn 기재값 → 열(축)로 읽으면  Z축 = (0, -0.432,  0.902)
실제 GlobalTransform            Z축 = (0, +0.432,  0.902)
```

행 순서로 읽어야 실측과 일치한다. 올바르게 다시 계산하니 손패 카메라는 **카드 정중앙을
시선축 내적 1.000으로 정확히 겨냥**하고 있었다. 사용자가 제대로 맞춰둔 걸 내가 잘못 읽은
것이다.

### Godot의 앞면 winding은 **시계방향**이다

절차적 메쉬를 만들려면 반드시 알아야 하는데, 틀리면 카드가 앞에서 안 보이고 뒤에서만
보인다. 추측하지 않고 `QuadMesh`(확실히 +Z를 향함)의 실제 배열을 뽑아서 확인했다:

```
VERTEX: [(1,-2,0), (-1,-2,0), (1,2,0), (-1,2,0)]
NORMAL: (0, 0, 1)
INDEX:  [0, 1, 2,  1, 3, 2]
```

첫 삼각형의 오른손 법선 = `(0,0,-8)` → 선언된 노멀과 **반대**. 즉 보이는 쪽에서 봤을 때
시계방향이 앞면. UV 원점은 좌상단.

### `AtlasTexture`는 2D 전용 크롭이다

`Sprite2D`/`TextureRect`가 그릴 때 잘라내는 기능이고, **`StandardMaterial3D.AlbedoTexture`는
`Region`을 완전히 무시하고 원본 시트 전체를 샘플링한다.** 그래서 카드 한 장에 주먹·가위·보
아트가 전부 나왔다. `atlas.Atlas`를 직접 넣고 `Uv1Scale`/`Uv1Offset`으로 같은 크롭을
재현했다.

### `detect_3d`는 **코드로 할당한** 텍스처에는 안 걸린다

Godot의 "3D에서 쓰이면 자동으로 VRAM 압축으로 재임포트" 기능은 **에디터에서 3D 머티리얼에
꽂았을 때** 발동한다. 카드 앞면 아트는 런타임 코드로 할당하므로 영원히 발동하지 않고 2D
기본값(밉맵 없음)에 머문다.

| | CardSprite (앞면) | CardBackImage (뒷면) |
|---|---|---|
| `mipmaps/generate` | **false** | true |
| `detect_3d/compress_to` | **1 (미발동)** | 0 (발동 완료) |

뒷면은 이미 정상 전환돼 있어서 앞뒤 품질이 달랐다. 앞면도 밉맵을 켜고 `detect_3d`를
껐다(압축은 무손실 유지 — 306×139라 메모리가 무의미하고 선·문자가 있어 BC 압축은 손해).

### `surface_material_override`는 **메쉬가 있어야** 로드된다

카드 메쉬를 런타임 생성으로 바꾸면서 `.tscn`에서 메쉬를 뺐더니, 씬에 적어둔
`surface_material_override/0`이 **로드 시점에 조용히 버려졌다.** 서페이스 개수가 0이라
인덱스 0을 받아주지 않는다. `material_override`는 메쉬와 무관한 단순 프로퍼티라 정상
로드된다 — 헤드리스로 확인하고 그쪽으로 바꿨다.

### `Viewport.physics_object_picking`은 **기본 off**

3D에서 hover/click 신호가 아예 발생하지 않는다. `Area3D`를 붙이고 시그널을 연결해도
이 스위치 없이는 조용히 아무 일도 안 일어난다.

### 스켈레톤의 "global pose"는 씬 월드가 아니다

`GetBoneGlobalPose`의 "global"은 **본들 사이에서** global이라는 뜻이다. 진짜 월드 변환은
`skeleton.GlobalTransform * GetBoneGlobalPose(bone)`.

### 본의 축 규약 ≠ 카메라의 축 규약

리그의 머리 본은 **로컬 -Z가 "얼굴이 향하는 방향"이 아니다**(측정으로 확인). 본 basis를
카메라에 그대로 복사했더니 뒤를 봤다.

해결은 규약을 알아내는 게 아니라 **알 필요를 없애는 것**이었다. 시선 회전을 **카메라
자신의 rest basis 기준**으로 계산하고, 그 월드 델타를 본의 rest basis에 얹는다:

```
delta     = lookBasis * restCameraBasis.Inverse()
boneWorld = delta * restBoneWorldBasis
```

이 델타는 자기완결적이라 **네트워크로 그대로 보낼 수 있다.** yaw/pitch 숫자를 보냈다면
받는 쪽이 보내는 쪽의 카메라 규약을 알아야 했을 것이다.

## 3. 조용히 잘못 그려지고 있던 것들

에러도 경고도 없이 그냥 잘못 보이던 것들. 코드 리뷰로 찾았다.

### 앞뒷면 쿼드가 박스 표면과 정확히 동일 평면 (z-fighting)

카드 두께를 0.004 → 0.0005로 줄이면서 오프셋도 0.0021 → 0.00025로 같이 줄였는데,
`0.00025`는 정확히 박스의 절반 두께였다. 이전엔 0.0001만큼 앞이었던 게 **정확히 겹치게**
됐다.

수정은 오프셋 미세조정이 아니라 **동일 평면 자체를 없애는 것**이었다 —
[RoundedCardMesh](../Scripts/Match3D/RoundedCardMesh.cs)가 면과 옆벽을 따로 만들어
**모서리에서 직각으로 만나게** 한다. 겹치는 표면이 존재하지 않는다.

### 페이드 밴드 폭이 0

`DistanceFadeMinDistance == DistanceFadeMaxDistance == 0.4`. 디더 비율이
`(distance - MIN) / (MAX - MIN)`이라 **0으로 나눈다.** 페이드가 불규칙하게 동작했다.
지금은 상수 옆에 이 이유를 주석으로 박아뒀다.

### 카드 아트에 이미 둥근 모서리가 있었다

모서리를 둥글게 하기 전에 원본 픽셀을 재봤더니 **네 귀퉁이가 전부 알파 0**이었다.
아트에 이미 둥근 모서리가 그려져 있었던 것이다. 그런데 머티리얼이 불투명이라 알파가
무시되고, 임포트의 `fix_alpha_border`가 채운 색으로 렌더돼서 각진 사각형으로 보였다.

| | 모서리 반경 | 리전 폭 |
|---|---|---|
| 가위 | 6px | 91 |
| 바위 | 2px | 90.06946 |
| 보 | 2px | 92 |

**카드마다 반경도 폭도 다르다.** 알파 스시저로 자르면 카드별로 모서리가 달라지고 뒷면·
테두리는 각진 채 남는다. 그래서 지오메트리로 둥글리는 쪽을 택했다 — 앞/뒤/테두리 실루엣이
하나로 일치하는 유일한 방법이다.

(바위의 `90.06946`은 에디터에서 드래그하다 어긋난 값으로 보인다. 아직 안 고쳤다.)

## 4. `[Tool]`과 `Instantiate<T>()`

에디터에서 카드가 안 보이는 문제를 여러 차례 오진했고, 사용자가 붙여준 디버거 출력이
답이었다:

```
System.InvalidCastException: Unable to cast object of type 'Godot.Node3D'
to type 'RockAndScissPaper.Match3D.CardView'
```

**`[Tool]` 컨텍스트에서 루트 스크립트가 `[Tool]`이 아닌 씬을 `Instantiate<T>()`하면
맨 `Node3D`가 나온다.** 스크립트가 에디터에서 붙지 않기 때문이다. 예외는 캐스트에서
터지는데 원인은 전혀 다른 파일에 있다.

(이후 사용자 요청으로 `CharacterIdlePose` 외의 `[Tool]`은 전부 뗐다.)

## 5. 이벤트가 안 오는 경우

### `mouse_exited`는 마우스 모드가 바뀔 때 안 온다

손패뷰를 벗어나면 마우스가 다시 캡처되는데, **커서가 카드 경계를 넘은 적이 없으므로**
`mouse_exited`가 발생하지 않는다. 테두리가 켜진 채 남는다. 이벤트로 상태를 유지하지 않고
매 프레임 판정하는 쪽으로 바꿨다 — 카드 5장짜리에 `_Process`는 공짜에 가깝고, 크로스노드
배선 없이 모든 경우가 닫힌다.

### `Skeleton3D.PoseUpdated` 안에서 포즈를 세팅하면 재귀한다

핸들러 안에서 포즈 세터를 부르면 시그널이 다시 발생할 수 있다. **에러 없이 그냥 멈춘다.**
`_Process`로 옮겼다.

## 6. 실제로 통했던 검증 방법

이 문서의 거의 모든 항목이 아래 넷 중 하나로 잡혔다.

1. **헤드리스 실행 + 임시 `GD.Print`.**
   `godot --headless --path . <scene> --quit-after N`. 카메라-머리 거리, 본 월드 좌표,
   basis 행렬식, 메쉬 AABB, 삼각형 수를 실제 숫자로 뽑는다. 내 가설을 반복적으로
   반증했다. 측정 후 **즉시 제거**.

2. **`GodotSharp.dll` 리플렉션.**
   설치된 4.7 어셈블리를 직접 로드해서 메서드 시그니처와 `[Obsolete]` 여부를 확인.
   `SetBoneGlobalPoseOverride`가 폐기됐다는 사실이 여기서 나왔다.

3. **엔진 자체 자료구조를 정답지로 쓰기.**
   winding 규약을 추측하는 대신 `QuadMesh.get_mesh_arrays()`를 뜯었다. 엔진이 만든
   메쉬는 정의상 규약을 지키고 있다.

4. **통합 지점을 실제로 쏴보기.**
   피킹이 되는지 확인하려고 손패 카메라 위치에서 레이캐스트를 날려 `PickArea`에
   맞는지, 어디에 맞는지를 찍었다 — `(0.018, 0.770, 0.341)`, 예측한 가운데 카드
   위치와 일치.

**공통점:** 전부 "그럴 것이다"를 "이 숫자다"로 바꾸는 작업이다. 이 프로젝트에서 오진한
경우는 예외 없이 측정을 건너뛴 경우였다.

## 7. 남은 것 / 아직 검증 안 된 것

- **머리 시선 동기화는 2인스턴스로 확인 안 했다.** 빌드·헤드리스·테스트는 통과했지만
  실제 RPC 왕복은 미검증이다. [CLAUDE.md](../CLAUDE.md)가 요구하는 검증 방식이 아직
  안 됐다.
- **`HeadFollowCamera`의 이름이 안 맞는다.** 이제 뷰 전환까지 한다. 제출 흐름이 붙어서
  카메라 상태가 3개 이상 되면 `MatchCameraRig` 같은 걸로 분리하는 게 맞다.
- **`CardView.tscn`을 에디터에서 열면 아무것도 안 보인다** (메쉬가 런타임 생성).
  `[Tool]`을 다시 붙이면 해결되지만 지금은 안 붙였다.
- **테이블 위 제출 카드도 클릭된다.** 손패만으로 좁히는 건 실제 손패 시스템이 생겨야
  의미가 있다.
- **코드 리뷰에서 나온 나머지:** 아틀라스 가장자리 블리딩(`TextureRepeat = false`),
  카드 리전 비율 불일치, 배치 코드 두 갈래(슬롯이 스케일 보정 vs 카드가 스케일 보정).
