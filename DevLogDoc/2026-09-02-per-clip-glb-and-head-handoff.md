# 2026-09-02 — 애니메이션은 클립 하나당 파일 하나로, 머리는 넘겨줄 때도 부드럽게

**태그:** `#3d` `#troubleshooting`

보 승리 애니메이션을 붙이면서 "블렌더에서 만든 클립 하나를 어떻게 기존 라이브러리에
합치나"는 질문이 "합치지 말고 그냥 따로 두면 되지 않나"로 결론났다. 그 과정에서 내보낸
파일을 두 번 검사해서 문제를 걸러냈다. 결과는 커밋 `61ddf0f`(보 승리)와
`048cc9d`(머리 핸드오프).

---

## 1. 애니메이션 파일을 검사하는 스크립트를 먼저 만들었다

`main_amature_nomesh.glb`에 새 클립을 합치려던 첫 시도(`Paper_animation_only.glb`,
55MB)를 열어보니 세 가지가 잘못돼 있었다:

| 증상 | 실제 원인 |
|---|---|
| 55,382 KB (기존 파일은 266 KB) | 아마추어 선택 없이 씬 전체가 나감 — 메쉬 13개, 텍스처 4개 포함 |
| 루트가 `Armature`, `Armature.001`, `Cube.001` 셋 | 다른 blend의 아마추어가 같이 딸려옴 |
| `Anim_StabScissor_Baked`가 없음 | 다른 blend 파일이라 그 액션 자체가 그 파일엔 없음 |

**세 번째가 제일 위험했다** — 그대로 `main_amature_nomesh.glb`를 덮어썼다면 가위
찌르기와 그날 앞서 붙인 피 효과가 통째로 사라졌을 것이다. glTF는 JSON + 바이너리
버퍼라 파이썬으로 직접 파싱해서 확인할 수 있다 — 노드 목록, 루트, 메쉬/이미지 개수,
각 애니메이션의 채널 수와 대상 본을 뽑는 스크립트를 만들어뒀다. 재export가 있을 때마다
같은 검사를 돌린다:

```
python check_glb.py Assets/Models/<파일>.glb
# 루트가 Armature 하나인지, 노드 68개인지, 메쉬/이미지가 0인지,
# 필요한 클립이 다 있고 전부 201채널인지 확인
```

두 번째 재export(`Paper_animation_only.glb`, 240KB)는 구조가 완벽했다 — 노드 목록이
기존 파일과 **순서까지 정확히 일치**해서 트랙 경로가 깨질 걱정이 없었다. 그런데
`Anim_StabScissor_Baked`가 여전히 없었다. 다른 blend 파일에서 작업했으니 당연한
결과였다.

## 2. 합치는 대신, 클립 하나당 `.glb` 하나로 간다

여기서 원래 계획(기존 blend에 액션을 append해서 한 파일로 유지)을 접었다.
`AnimationPlayer`는 **라이브러리를 여러 개** 붙들 수 있다는 걸 다시 확인하고, 그냥
새 파일을 두 번째 라이브러리로 얹었다.

```
main_amature_nomesh.glb   → &""       (빈 키, 기존 세 클립)
Paper_animation_only.glb  → &"paper"  (Character.tscn에서 이 이름으로 등록)
```

호출은 `Play("paper/Anim_Paper_Flip_Baked")`처럼 라이브러리 이름이 접두사로 붙는다.

**임포트 설정이 기본값과 다르다는 걸 놓칠 뻔했다.** `.glb`를 프로젝트에 처음 떨어뜨리면
Godot은 기본으로 `importer="scene"`(PackedScene)을 쓴다. 애니메이션 전용 파일은
`importer="animation_library"`로 `.import`를 직접 고쳐써야 `AnimationLibrary` 타입으로
들어온다 — 기존 `main_amature_nomesh.glb.import`를 참고해서 맞췄다.

이 결정 뒤로는 새 클립이 생길 때마다:
1. 새 `.glb` 하나 (블렌더가 그 clip이 있는 파일에서 바로 export)
2. `.import`를 `animation_library`로 고쳐서 재임포트
3. `Character.tscn`에 라이브러리 한 줄, 이름 하나
4. 코드에서 `"<이름>/<클립>"`으로 참조

**기존 파일에 계속 합치는 방식이 하지 못했던 것**: 합치려면 매번 "모든 클립을 가진
마스터 blend"가 하나 있어야 하고, 그 왕복 자체가 오늘 클립 하나를 잃을 뻔한 원인이었다.
분리된 파일은 서로의 존재를 몰라도 되고, 없는 클립을 실수로 지울 방법이 없다.

## 3. 임팩트 시각도 같은 방식으로 쟀다

`Anim_Paper_Flip_Baked`의 오른팔 체인 각속도: 0.600s에 23.1 rad/s로 정점, 0.667s에
11.2로 반토막. 그 감속을 손바닥이 책상에 닿는 순간으로 읽어 `PAPER_IMPACT_SECONDS = 0.65f`.
카메라 셰이크 강도는 0.55 — 가위 0.7, 바위 1.0보다 약하게 뒀다. 보는 사람이 아니라
책상을 치는 거라, 테이블이 튀어야지 머리가 흔들리면 안 된다.

이걸로 승리 동작 3종(바위/가위/보) 전부에 연출이 생겼다 — 전에는 보로 이긴 라운드가
아무것도 안 그렸다.

## 4. 머리가 애니메이션 끝에 툭 끊겨서 돌아왔다

증상: 펀치가 끝나는 프레임에 머리가 애니메이션 마지막 포즈에서 **마우스가 가리키는
방향으로 순간이동**했다. 원인은 8월 31일 붙인 가드(`if (!IsPlaying()) Apply(...)`)의
당연한 귀결이었다 — 애니메이션이 도는 동안 본을 아예 안 건드리다가, 멈추는 그 한
프레임에 마우스 방향 전체를 한 번에 써넣었다. 사이에 아무것도 없으니 끊길 수밖에
없었다. `HeadFollowCamera`와 `RemoteHeadLook` 둘 다 같은 구조였다.

### 해법 — 본의 "지금 실제 자세"에서 slerp

[`BoneLookRotator`](../Scripts/Match3D/BoneLookRotator.cs)에 `lookAuthority`(0~1)를
추가했다. **본이 지금 실제로 있는 자세**(애니메이션 도중이면 클립의 포즈, 아니면 지난
프레임 이 코드 자신이 쓴 값)에서 원하는 방향으로 slerp한다. authority가 1이면 결과가
정확히 마우스 방향에 떨어지므로 평상시 동작은 그대로다.

**"본이 지금 있는 자세"를 읽는 게 핵심**이었다 — 클립의 포즈를 전달받는 방식이었다면
호출자가 클립의 상태를 알아야 했을 것이다. 대신 매 프레임 실제 본의 월드 포즈를 읽어서
거기서부터 떠나므로, 클립이 어느 포즈에서 끝나든 이 코드는 그걸 몰라도 된다.

속도는 비대칭이다: 클립이 가져갈 때 0.12s, 마우스가 돌려받을 때 0.35s. 가져가는 쪽은
빨라도 된다 — 애니메이션 자체의 움직임이 전환을 가려준다. 돌려주는 쪽은 가려줄 게
없어서, 빠르면 그게 곧 이번에 고치려던 그 팝(pop)이다.

로컬(내 머리)과 리모트(내 화면의 상대 머리) 양쪽 다 같은 상수로 고쳤다 — 한쪽만
고치면 내 펀치는 자연스러운데 상대 화면에서 보는 내 머리는 여전히 끊기는, 8월 31일과
같은 종류의 반쪽 수정이 됐을 것이다.

## 5. 그 밖: 메뉴 음악을 껐다

`TitleScreenUI`에서 `PlayMainMenuMusic()` 호출 한 줄을 주석 처리했다(`14151db`). 매치
진입 시 `MatchWorldView`가 이미 `StopMusic()`을 부르고 있었으니, 시작을 안 하는 것만으로
게임 전체가 무음이 됐다. 지금 들어있는 트랙이 2D 시절 톤이라 지금 방향과 안 맞는다는
판단 — `AudioManager`와 에셋은 그대로 둬서 되돌리는 건 주석 한 줄이다. 설정 메뉴의 음악
볼륨 슬라이더는 지금 아무 일도 안 하는 채로 남아 있다 — 음악을 완전히 안 쓰기로 정하면
그때 씬에서 같이 뗀다.
