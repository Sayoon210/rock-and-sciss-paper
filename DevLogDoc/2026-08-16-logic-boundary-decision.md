# 2026-08-16 — 로직 경계와 테스트 전략 결정

Autoload에 게임 로직을 어디까지 넣을지에서 출발해서, 최종적으로 "순수 C# 경계를 긋고 테스트 프레임워크를 도입한다"까지 온 흐름.

## 출발점: 게임 로직도 결국 Autoload에 넣는 거 아닌가?

- 처음 의문: Autoload이 전역 매니저니까 게임 로직(라운드 판정, 스코어, 덱 관리)도 거기 들어가는 게 자연스럽지 않나?
- 결론: **넣지 않는다.** 경계를 이렇게 나눔 — *Autoload은 소유하고 중계한다. 규칙은 소유당하는 순수 클래스가 안다.*
  - `GameState` (Autoload) — 매치 객체 소유, 리셋, RPC 수신, UI용 시그널 발신
  - `MatchSession` / `RoundResolver` (`Scripts/Game/`의 순수 C#) — 판정 순서, 스코어, 덱/패/소멸 처리
- **Why 1**: 호스트 권위 구조라 규칙은 한쪽에서만 실행되는데, Autoload은 호스트/클라 양쪽에 다 로드됨. Autoload 자체가 규칙이면 클라에선 "절반만 살아있는 싱글톤"이 되고 desync의 온상이 됨.
- **Why 2**: 판정 분기가 실제로 복잡함 (조커 > 리셋 > 그 외 특수 > 일반, 무승부, 소멸 vs 덱바닥 복귀). 검증 비용이 아키텍처를 결정할 만큼 큼.

## 알게 된 것: Autoload은 조건부 로딩이 불가능하다

- 궁금했던 것: 호스트만 연산하는데, 호스트에만 Autoload을 로드할 수 있나?
- 답: **불가능.** `project.godot`에 등록된 Autoload은 게임 시작 시 모든 인스턴스에 무조건 로드됨. 애초에 그 시점엔 아직 호스트인지 클라인지 결정도 안 됨(유저가 "방 만들기"/"참가하기"를 누르기 전).
- 따라서 **로딩을 나누는 게 아니라 런타임에 권한으로 분기**하는 게 유일한 방법.
- 채택한 방식: `GameState._session`은 호스트에서만 non-null, 클라에선 항상 null. 표시용 `View`만 양쪽이 공유.
- **Why**: 클라에서 실수로 규칙을 돌리려 하면 null로 즉시 터짐. 양쪽 다 "진짜" 세션을 들고 조용히 어긋나다가 몇 라운드 뒤에 원인 불명 desync로 터지는 것보다 훨씬 나음.

## 공부: static Instance 접근 패턴

- Godot 기본 접근법은 문자열 경로 — `GetNode<NetworkManager>("/root/NetworkManager")`.
  - 문제 1: `GetNode`는 `Node`의 메서드라 호출부도 `Node`여야 함. 순수 C# 클래스에선 못 씀.
  - 문제 2: 경로가 그냥 문자열이라 오타 내도 빌드는 통과하고 실행 중에 터짐.
- 대안: `public static NetworkManager Instance { get; private set; }` + `_EnterTree()`에서 `Instance = this`.
  - `static`은 클래스 자체에 붙는 멤버라 객체 없이 `NetworkManager.Instance`로 접근 가능.
  - 오타 내면 **컴파일 에러** — 실행 전에 잡힘.
- **핵심 이해**: 이건 Autoload이라 자동으로 되는 게 아니라 직접 두 줄 써야 생기는 것. Autoload이 해주는 건 *"인스턴스 하나뿐 + 세션 내내 생존"* 보장이고, **그 보장 덕분에 static 필드에 담아도 안전한 것**. 일반 노드였다면 중복 인스턴스나 해제된 객체 참조 문제가 생김.
- `_Ready()`가 아니라 `_EnterTree()`에 넣는 이유: 더 먼저 실행돼서 다른 노드의 `_Ready()`에서 이미 쓸 수 있음.

## 갈림길: Godot 띄워서 확인 vs 테스트 프레임워크

판정 로직을 어떻게 검증할 것인가에서 두 갈래가 나옴.

**A. Godot 띄워서 확인 (경계 안 그음)**
- `Scripts/Game/`에서 `CardData : Resource`를 그냥 사용. 덱이 카드 객체 리스트라 카드 정보에 바로 접근 가능 — 코드가 직관적.
- 대신 검증하려면: 게임 실행 → 방 만들기 → 인스턴스 하나 더 띄워 접속 → 해당 카드가 손에 들어올 때까지 플레이 → 상대도 특정 카드를 내야 함 → 눈으로 확인. **한 조합에 몇 분.**

**B. 경계 긋기 + 테스트 프레임워크 (채택)**
- `Scripts/Game/`에 Godot 타입 전면 금지. `Resource`도 포함 — Godot의 C# 타입은 네이티브 C++ 객체 래퍼라 Godot 런타임 없이는 생성 자체가 안 됨.
- 그 결과 덱이 `List<CardData>`가 아니라 `List<CardKind>` (식별자 리스트)가 됨. 판정은 "이건 조커다"까지만 알고, 이름/아트는 UI에서 `CardDatabase`로 조회.
- 검증은 함수 직접 호출 — 창도 씬도 네트워크도 없이 0.1초. 수십 가지 조합 자동 실행.

## 결정

- **B 채택.** 경계를 긋고 테스트 프레임워크를 도입한다.
- **Why**: 검증할 조합이 실제로 많음(조커 × 6종 특수, 리셋 충돌, 무승부, 소멸 vs 덱바닥). A안은 조합당 비용이 너무 커서 결국 검증을 안 하게 되고, 그러면 판정 버그가 플레이 중에야 발견됨.
- **전제 조건**: 이 판단은 "테스트를 실제로 쓴다"에 걸려 있음. 안 쓸 거면 경계는 순수 비용이므로 A가 맞음. 쓰기로 했으므로 B.
- **부수 이득**: 경계 덕분에 Godot 전용 테스트 도구(GdUnit4 등) 없이 평범한 .NET 표준 xUnit을 쓸 수 있음.
- 관련 지침을 순수 로직 쪽(이후 `Core/`로 이동 — [GameLogic/CLAUDE.md](../GameLogic/CLAUDE.md))과 [Scripts/Autoload/CLAUDE.md](../Scripts/Autoload/CLAUDE.md)에 반영.
